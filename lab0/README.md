# Лабораторная работа №0 — Ветеринарная база кошек

## Цель работы

Собрать простое веб-приложение из трёх компонентов — фронтенд, бэкенд и база данных, — чтобы в следующих лабораторных настраивать вокруг него инфраструктуру: nginx, Docker и CI/CD. Программирование здесь не является целью, поэтому сервис намеренно простой: главное — понять, как части общаются между собой и как всё это потом контейнеризовать.

## Стек

- **Backend:** Kotlin 2.2 + Ktor 3.1.3 + Exposed
- **DB:** PostgreSQL 16 (отдельный сетевой сервис)
- **Frontend:** HTML + JavaScript
- **Сборка:** Gradle
 поэтому фронт и API живут на одном порту и не требуют отдельного веб-сервера.

## Функционал приложения

Наше приложение — это веб-интерфейс для ветеринарной клиники, который позволяет вести учёт кошек. Пользователю доступен следующий функционал:

- **Просмотр списка кошек.** При открытии страницы загружается список всех животных, когда-либо добавленных в базу данных.
- **Добавление новой кошки.** Через форму на странице можно добавить кошку, указав её кличку и цвет. После отправки данные сохраняются в PostgreSQL.
- **Удаление записи.** У каждой кошки в списке есть кнопка «Выписать», которая безвозвратно удаляет запись из базы данных.
- **Проверка работоспособности.** Сервер имеет health-check эндпоинт для проверки того, что бэкенд запущен и отвечает на запросы.

## Состав приложения и архитектура

Наше приложение состоит из трёх независимых компонентов, которые общаются между собой по сети. Разделение на части сделано специально — чтобы в следующих лабораторных работах каждую из них можно было упаковать в отдельный Docker-контейнер.

1. **База данных (PostgreSQL).** 
   Отдельный сетевой сервис, который работает в фоне и слушает порт 5432. Отвечает за долговременное хранение данных. В базе `vet_clinic` создана таблица `cats`, где хранятся записи о кошках (id, кличка, цвет, время добавления). Без неё данные бы исчезали после перезапуска сервера.

2. **Бэкенд (Kotlin + Ktor).** 
   Серверное приложение, которое запускается на порту 8080. Выполняет роль связующего звена: принимает HTTP-запросы от пользователя, обрабатывает бизнес-логику (валидация данных) и через JDBC-драйвер обращается к базе данных. Также бэкенд отвечает за раздачу статических файлов (фронтенда).

3. **Фронтенд (HTML + JavaScript).** 
   Пользовательский интерфейс, который открывается в браузере. Это одностраничный сайт с формой добавления и списком кошек. Фронтенд не имеет прямого доступа к базе данных — он общается только с бэкендом через API, отправляя запросы и получая JSON-ответы.

**Как они взаимодействуют:**
Цепочка запроса выглядит так: пользователь вводит данные на фронтенде → JavaScript отправляет HTTP-запрос (например, `POST /api/cats`) → бэкенд на Ktor принимает запрос → через JDBC делает SQL-запрос к PostgreSQL → база данных сохраняет запись и возвращает результат → бэкенд отдаёт JSON-ответ фронтенду → страница перерисовывается.

## Как запустить приложение

Для запуска вам понадобятся: установленный JDK 21, PostgreSQL 16 и Gradle (или использовать встроенный `gradlew`).

### 1. Подготовка базы данных

Убедитесь, что PostgreSQL запущен. Создайте базу данных и таблицу:

```bash
# Создаем базу данных
createdb vet_clinic

# Заходим в нее
psql -d vet_clinic
```

В открывшемся консольном клиенте PostgreSQL выполните SQL-запрос для создания таблицы:

```sql
CREATE TABLE cats (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    color TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

\q
```

### 2. Запуск бэкенда

Откройте терминал в корневой папке проекта (`lab0`) и запустите сервер с помощью Gradle:

```bash
./gradlew run
```

Дождитесь появления в логах сообщения о том, что сервер запущен:
```text
INFO  ktor.application - Responding at http://0.0.0.0:8080
```

### 3. Использование

После успешного запуска сервера откройте браузер и перейдите по адресу:
**[http://localhost:8080](http://localhost:8080)**

Вы увидите форму для добавления кошек и список уже добавленных записей.

## Выводы

Лаба 0 дала понимание, как устроено взаимодействие трёх компонентов: фронт общается с бэком по HTTP, бэк ходит в базу через JDBC, база хранит данные. Именно такая архитектура нужна, чтобы в следующих лабах каждую часть можно было вынести в отдельный контейнер. Отдельный урок — про зависимости: в экосистеме Kotlin/JVM важно следить за версиями, потому что BOM покрывает не все модули, а несовпадение версий ломает сборку.
