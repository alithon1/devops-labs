# Лабораторная работа №1 — nginx

## Цель работы
Настроить nginx в качестве единой точки входа и балансировщика нагрузки перед сервисом из Лабы 0. ### 4. Дополнительные настройки nginx и проверка

Для выполнения всех требований в конфиг nginx (`lab1.conf`) были добавлены дополнительные директивы.

**Своя страница 404**
В папке `lab1/www` был создан файл `404.html`. В конфиг добавлены строки:
```nginx
error_page 404 /404.html;
location = /404.html {
    root /Users/cubelime/Desktop/devops-labs/lab1/www;
    internal;
}
```

**Псевдоним пути (alias) для `/docs`**
Создана папка с документацией и добавлен блок в конфиг:
```bash
mkdir -p ~/Desktop/devops-labs/lab1/docs
echo "Это документация нашего проекта" > ~/Desktop/devops-labs/lab1/docs/readme.txt
```
```nginx
location /docs {
    alias /Users/cubelime/Desktop/devops-labs/lab1/docs/;
}
```

**Виртуальные хосты (`second.local`)**
Домен добавлен в `/etc/hosts`. В конфиг nginx добавлен новый `server`:
```nginx
server {
    listen 443 ssl;
    server_name second.local;
    ssl_certificate ... (путь к сертификату)
    ssl_certificate_key ... (путь к ключу)
    location / {
        return 200 "Это второй сайт (second.local)\n";
    }
}
```

**Ограничение частоты запросов (`limit_req`)**
Добавлена зона лимита и ограничение для API (с принудительным статусом 429):
```nginx
limit_req_zone $binary_remote_addr zone=mylimit:10m rate=2r/s;

location /api {
    limit_req zone=mylimit burst=3 nodelay;
    limit_req_status 429;
    ...
}
```

**Базовая авторизация для `/admin` и трудности с ней**

**Скрипт автоматической проверки**
Чтобы не проверять каждый пункт вручную, я написала bash-скрипт, который автоматизирует весь процесс. С самим кодом скрипта можно ознакомиться по ссылке: [check.sh](check.sh).

Создан файл с паролем:
```bash
htpasswd -c -b /opt/homebrew/etc/nginx/.htpasswd admin qwerty123
```

Изначально я добавила блок `/admin` с директивой `return 200`, но nginx игнорировал `auth_basic` и пускал всех подряд. При проверке через `curl` отдавался код 200 даже без пароля. Я выяснила, что `return` имеет приоритет над проверкой авторизации. Тогда я изменила подход — убрала `return` и указала `root` с файлом:
```nginx
location /admin {
    auth_basic "Admin Area";
    auth_basic_user_file /opt/homebrew/etc/nginx/.htpasswd;
    root /Users/cubelime/Desktop/devops-labs/lab1/www;
    try_files /admin.html =404;
}
```

После этого без пароля nginx начал отдавать `401 Unauthorized`, но с правильным паролем тоже отдавал 401. Оказалось, что nginx не хватало прав на чтение файла `.htpasswd`. Я выдала их:
```bash
sudo chmod 644 /opt/homebrew/etc/nginx/.htpasswd
```

Я остановилось и вовремя посмотрела сам скрипт `check.sh`, выяснилось, что все эти проблемы были в самом скрипте — там была опечатка в пароле! После её исправления все проверки прошли успешно.

# Задание со звёздочкой: поиск уязвимостей

В рамках дополнительного задания я провела анализ безопасности моего локального сервера. Целью было не нанесение вреда, а проверка того, как ошибки в конфигурации nginx могут открыть доступ к информации, которая не предназначена для обычных пользователей. Я решила проверить три популярных вектора атак: Path Traversal, перебор директорий (Fuzzing) и утечку служебной информации. 

### 1. Проверка на Path Traversal (Off-by-slash)
Первое, что я решила проверить — это уязвимость под названием Path Traversal (или «обход директории»). В nginx она часто возникает из-за невнимательности при настройке директивы `alias`. Если в блоке `location` не поставить завершающий слэш, а в самом `alias` его указать, сервер может неправильно склеить путь. Это позволяет злоумышленнику с помощью последовательности `../` выйти за пределы разрешённой папки и прочитать файлы, которые лежат в других директориях.

Сначала я добавила одного котика в базу:

Затем проверила мой конфиг, там блок для документации выглядит так:
```nginx
location /docs {
    alias /Users/cubelime/Desktop/devops-labs/lab1/docs/;
}
```

Так как здесь есть потенциальная ошибка (нет слэша после `/docs`), я попыталась прочитать файл `README.md` из соседней папки `lab0`, которая находится уровнем выше. Для этого я использовала утилиту `curl` с флагом `--path-as-is`, который запрещает клиенту самостоятельно нормализовать путь, отправляя его на сервер в исходном виде:

```bash

```

Это означает, что nginx успешно справился с нормализацией путей и не позволил мне выйти за пределы папки `docs`. Несмотря на то, что конфигурация выглядит уязвимой, современные версии nginx блокируют такие переходы. Я сделала вывод, что мой сервер защищен от этой атаки.

### 2. Перебор скрытых страниц (Fuzzing)
Второй этап — это проверка того, какие еще страницы могут существовать на сервере, помимо тех, что я создала специально. Злоумышленники часто используют метод фаззинга (fuzzing), при котором специальная программа подставляет слова из словаря в URL и смотрит на ответы сервера. Если сервер отвечает кодом `200` или `401`, значит, страница существует.

### 3. Утечка информации о версии сервера (Information Disclosure)
Третья уязвимость, которую я проверила, связана с раскрытием служебной информации. По умолчанию nginx сообщает всем клиентам свою точную версию в HTTP-заголовке `Server`. На первый взгляд это кажется безобидным, но для злоумышленника это ценная информация: зная точную версию сервера, он может найти конкретные уязвимости (CVE) и эксплойты, которые работают именно на этой версии.

Я отправила запрос с флагом `-I`, чтобы посмотреть только заголовки ответа:
```bash
curl -kI https://localhost
```

**Результат проверки:** В ответе сервера я увидела строку `Server: nginx/1.31.8`. Это подтверждает утечку информации.

### Итоги задания со звёздочкой

Проведя эти проверки, я поняла, что уязвимости часто возникают из-за мелочей, а не сложных хакерских атак. Мой сервер оказался защищен от обхода директорий (Path Traversal). При этом `ffuf` — это лишь инструмент разведки, но он показал, что скрытые разделы (например, админку) легко найти, если не защищать их должным образом. Кроме того, открытый заголовок с версией сервера выдает лишнюю информацию атакующему. Теперь я знаю, что при настройке важно не только ставить пароли, но и скрывать служебные данные о сервере.
